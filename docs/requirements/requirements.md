## 1. プロジェクト概要

**RankMe** は、女性の顔写真をもとに**プロのスカウト実務基準に対する近さ**をAIで数値化し、その根拠に基づいた改善アドバイスを提示する**視覚評価プラットフォーム**である。

### 1.1 システムの目的

- 一般的な美醜評価ではなく、**スカウト現場の評価基準の再現**を目的とする
- AIは教師データとの類似度の数学的計算により、主観を排した客観的なランク（1〜10）を算出する
- 判定結果に基づき、上位ランクに近づくための具体的な改善アドバイスを生成・提示する

### 1.2 システムの特徴

- **判定エンジン**: Docker Compose（GPU対応）で起動可能。モデル・学習方法を複数実装し設定で切り替え可能
- **データ保存**: 診断結果は外部DB（GCP: Cloud SQL / Firestore）に保存
- **教師データ**: プロのスカウト実務者による10段階ラベリング（各ランク100枚、合計1,000枚）
- **拡張性**: 顔診断に限らず、教師データと評価基準を差し替えることで他ドメインの視覚評価にも応用可能

### 1.3 診断の流れ

1. ユーザーが顔写真をアップロードする
2. AIが教師データとの類似度から**ランク（1〜10）**を判定する
3. 判定結果に基づき、上位ランクに近づくための**改善アドバイス**を生成する
4. **診断レポート**を表示する（ランク + 改善アドバイス + 客観性明示文）

## 2. 機能要件

### FR-001: 画像アップロード

- **ID**: F-001
- **優先度**: 必須
- **説明**: ユーザーがWeb画面から顔写真を1枚アップロードできる
- **受入基準**:
  - [ ] ドラッグ＆ドロップまたはファイル選択でアップロード可能
  - [ ] JPEG, PNG 形式に対応
  - [ ] 最大ファイルサイズ制限あり（5MB）
  - [ ] アップロード中のプログレス表示
  - [ ] 不正なファイル形式の場合エラーメッセージ表示
  - [ ] アップロード領域はミニマルなUI（ダッシュ枠線 + アイコン）

### FR-002: ランク判定（AI）

- **ID**: F-002
- **優先度**: 必須
- **説明**: 教師データとの類似度に基づきランク（1〜10）を算出する
- **受入基準**:
  - [ ] 顔画像1枚を入力としてランク（1〜10）を返却
  - [ ] 判定は教師データとの類似度の数学的計算に基づく（主観判断なし）
  - [ ] 判定時間は5秒以内を目標
  - [ ] AI推論サービスがダウンしている場合、適切なエラーメッセージ表示
  - [ ] 共通インターフェース（POST /predict）に準拠

### FR-003: 改善アドバイス生成

- **ID**: F-003
- **優先度**: 必須
- **説明**: 判定結果と教師データの傾向から、上位ランク向けの改善ポイントを提示する
- **受入基準**:
  - [ ] ランク結果に基づく具体的な改善アドバイスを生成
  - [ ] 上位ランクに近づくためのポイントが明確に記述される
  - [ ] テキスト形式で提示（類似度の生値はユーザーに非表示）
  - [ ] 改善アドバイスは3〜5項目で構成

### FR-004: 診断レポート表示

- **ID**: F-004
- **優先度**: 必須
- **説明**: 現在のランクと改善アドバイスのみを表示する
- **受入基準**:
  - [ ] 顔画像 + ランク数値 + 改善アドバイスをシンプルに表示
  - [ ] 客観性明示文を表示:「本判定は、選別済み画像データとの類似度および傾向分析に基づく客観的結果です。」
  - [ ] 免責文を表示:「個人の価値や魅力を断定するものではありません。」
  - [ ] 「もう一度診断」ボタンでトップ画面へ遷移可能
  - [ ] 余計な要素を排した簡潔な「診断書」レイアウト

### FR-005: 診断結果のDB保存

- **ID**: F-005
- **優先度**: 必須
- **説明**: 診断結果（ランク・アドバイス等）をDBに保存する。DBは外部インフラ（GCP想定）とする
- **受入基準**:
  - [ ] 診断結果（ランク、改善アドバイス、診断日時、識別用ID）が保存される
  - [ ] アップロード画像は保存しない（判定用のみ）
  - [ ] GCP上のDB（Cloud SQL / Firestore）に接続
  - [ ] 保存失敗時にリトライまたはエラーハンドリング
  - [ ] 環境変数で接続先を指定

### FR-006: 履歴表示

- **ID**: F-006
- **優先度**: 必須
- **説明**: 保存した診断結果の履歴を一覧・詳細表示する
- **受入基準**:
  - [ ] 履歴一覧画面で過去の診断結果を表示
  - [ ] 各件のランク・アドバイスの詳細表示が可能
  - [ ] 外部DB（GCP）から取得して表示
  - [ ] トップ画面から「履歴を見る」リンクでアクセス可能
  - [ ] 日時・ランクの情報を一覧に表示

### FR-007: 判定方法の切り替え

- **ID**: F-007
- **優先度**: 必須
- **説明**: AIのモデル・学習方法を複数実装し、設定で切り替え可能にする
- **受入基準**:
  - [ ] 環境変数・設定ファイルでエンジン切り替え（例: `RANKME_ENGINE=model_a`）
  - [ ] コード変更を伴わず切り替え可能
  - [ ] 共通インターフェース: 入力（顔画像1枚）→ 出力（ランク1〜10 + アドバイス生成情報）
  - [ ] Docker Compose 起動時に選択されたエンジンが動作
  - [ ] 複数エンジンを同一APIでルーティング可能な設計

### FR-008: 顔に点数をつけるUI

- **ID**: F-008
- **優先度**: 必須
- **説明**: 診断結果を顔に対して点数（ランク）をつけるシンプルなUIで表示する
- **受入基準**:
  - [ ] 顔写真とランク数値を一目で分かるように表示
  - [ ] 余計な要素を排した簡潔な画面
  - [ ] ランク数値が視覚的に目立つデザイン（大きなフォント + アクセントカラー）
  - [ ] 顔写真 + スコア + 改善アドバイス + 客観性明示文の構成

### FR-009: ラベリング手動追加UI

- **ID**: F-009
- **優先度**: 必須
- **説明**: 教師データの拡張・再ラベリングのため、ラベリングを手動で追加するUIを用意する
- **受入基準**:
  - [ ] 画像を登録しランク（1〜10）を手動で付与可能
  - [ ] 一覧表示・編集・削除が可能（CRUD操作）
  - [ ] 認証不要・アクセス制御不要（管理者・ラベラー向け）
  - [ ] ラベリングデータは全判定方法で共通参照
  - [ ] ラベリング作業画面: 顔写真表示 + スコア入力

## 3. 非機能要件

### NFR-001: 認証

- ユーザー認証は**不要**とする
- 診断・履歴・ラベリングUI ともに認証なしで利用可能
- 将来的な認証追加に備え、CC-Auth設定のみ準備（セクション11参照）

### NFR-002: アクセス制御

- ラベリングUI へのアクセス制御は**不要**とする
- 権限の細分化は行わない
- 全ユーザーが全機能にアクセス可能

### NFR-003: 可用性

- 小規模・デモレベルを想定
- SLAは必要に応じて後から定義
- 単一障害点の最小化は推奨するが、冗長構成は必須としない

### NFR-004: セキュリティ

- アップロード画像は判定用のみとし、**保存しない、または短期保存に留める**
- 診断結果のみDB保存（画像データはDBに永続化しない）
- OWASP Top 10 対策（XSS, CSRF, インジェクション防止）
- ファイルアップロードのバリデーション（ファイル形式・サイズ制限）

### NFR-005: パフォーマンス

- 1枚あたりのAI判定時間: **5秒以内**を目標
- Webフロントの Lighthouse Performance: **90+**
- First Contentful Paint (FCP): **< 1.8s**
- Largest Contentful Paint (LCP): **< 2.5s**
- Cumulative Layout Shift (CLS): **< 0.1**

### NFR-006: 運用

- Docker Compose で起動・停止が**必須**
- AI推論は Docker Compose で **GPU を使用**（NVIDIA GPU）
- `docker compose up` でWeb + AIをまとめて起動可能
- 環境変数で判定エンジン・DB接続先を制御

### NFR-007: 拡張性

- 初期は小規模（デモレベル）
- 教師データと評価基準を差し替えることで、**他ドメインの視覚評価プラットフォーム**として拡張可能な設計とする
- 顔診断に限定せず、汎用的な視覚情報評価・改善支援に応用可能

## 7. システムアーキテクチャ概要

### 7.1 全体アーキテクチャ

```
[ユーザー]
     │
     ▼
[Webフロント (TypeScript/Next.js)]  ← 画像アップロード・診断レポート表示
     │
     │ HTTP/API
     ▼
[Webバックエンド / API (TypeScript/Node.js)]  ← リクエスト受付・AI呼び出し・アドバイス生成制御
     │
     ├─ 内部API ──► [AI推論サービス (Python/FastAPI)]  ← Docker Compose (GPU)
     │                  └─ 判定エンジン（設定で切り替え）
     │
     └─ 外部接続 ──► [DB (GCP Cloud SQL / Firestore)]  ← 診断結果保存・履歴
                      [GCS]  ← 教師データ格納
```

### 7.2 Docker Compose 構成

1つの `docker-compose.yml` で以下を起動できるようにする:

- **Webアプリ** (`web`): フロントエンド + APIサーバー + 改善アドバイス生成
- **AI推論サービス** (`ai`): ランク判定エンジン。モデル・学習方法は設定で切り替え

AI推論サービスはDocker Composeで**GPUを使用**する。NVIDIA GPUをコンテナに渡し、推論をGPUで実行する。

環境変数で使用する判定エンジンを切り替え可能とする（例: `RANKME_ENGINE=similarity_v1`）。

### 7.3 データベース（外部インフラ）

- **DBの配置**: 診断結果の保存用DBは Docker Compose の外に配置し、**外部インフラ**として運用
- **クラウド想定**: **GCP（Google Cloud Platform）** を想定
  - Cloud SQL（リレーショナル）: PostgreSQL
  - Firestore（ドキュメント型）
  - BigQuery（分析用 - オプション）
  - 実装時に選定
- **接続**: Webアプリは環境変数でDB接続先（GCP）を指定し、診断結果の保存・履歴取得を行う
- **教師データ格納**: GCS（Google Cloud Storage）を使用

### 7.4 API仕様（共通インターフェース）

#### POST /predict

AI判定APIの共通インターフェース。全判定エンジンがこの契約に従う。

**リクエスト**:
```
POST /predict
Content-Type: multipart/form-data

file: <顔画像ファイル (JPEG/PNG)>
```

**レスポンス**:
```json
{
  "rank": 7,
  "confidence": 0.85,
  "advice_context": {
    "nearest_upper_rank": 8,
    "improvement_areas": ["feature_a", "feature_b"],
    "similarity_scores": {}
  }
}
```

## 8. 教師データ仕様

### 8.1 基本仕様

| 項目 | 内容 |
|------|------|
| 評価段階 | **10段階**（ランク 1〜10） |
| データ規模 | **各ランク100枚、合計1,000枚**の顔画像 |
| ラベリング | **プロのスカウト実務者**による統一基準でラベリング |
| 目的 | 美醜の一般評価ではなく、**スカウト現場の評価基準の再現** |

### 8.2 ラベリング統一ルール

- 教師データのラベリング・アップデートは、**採用する学習方法やモデルに依存せず同一**とする
- 同一のラベル形式・データソースを全判定方法が参照する
- モデルや学習手法を差し替えてもラベリング運用は一つに統一する

### 8.3 ラベリングの追加・更新

- 教師データの拡張・再ラベリングは**手動追加UI**（FR-009）で行う
- 画像の登録とランク（1〜10）の付与を同一UIで実施
- 学習方法に限らず同一のデータソースを更新する

### 8.4 教師データ格納先

- GCS（Google Cloud Storage）に顔画像を格納
- ラベリング情報（画像パスとランクの対応）はDBに保存
- 教師データ容量目安: 1,000枚で約500MB

## 9. 判定エンジン仕様

### 9.1 判定の原則

- AIは**教師データとの類似度の数学的計算**（またはそれに準じる客観的算出）によりランク（1〜10）を決定する
- **主観的な判断は行わない**（類似度・学習結果に基づく客観的算出のみ）

### 9.2 複数実装・切り替え

- **設計方針**: 判定方法を複数実装できる形で設計する。モデルや学習方法を差し替え可能とする
- **切り替え方法**: 環境変数・設定ファイル・起動オプションなど、**コード変更を伴わず切り替えやすい方法**で実装する
  - 例: `RANKME_ENGINE=model_a` や設定で `engine: "similarity_v1"` を指定
- **共通インターフェース**: 入力（顔画像1枚）と出力（ランク 1〜10、および改善アドバイス生成に必要な情報）の契約を共通化し、実装ごとにこの契約を満たすことで差し替え可能にする
- **Docker Compose構成**: 起動するコンテナ内で選択された判定エンジン（1つ）が動く形、または複数エンジンを同じAPIでルーティングする形を想定

### 9.3 入出力仕様

| 項目 | 内容 |
|------|------|
| **入力** | 顔画像（1枚、JPEG/PNG） |
| **出力** | ランク（1〜10）+ 改善アドバイス生成モジュールへ渡す情報 |
| **プロトコル** | REST API（POST /predict、JSON返却） |

### 9.4 判定対象の定義

| 区分 | 内容 |
|------|------|
| **判定しているもの** | スカウト実務基準に対する近さ（教師データとの類似度に基づくランク） |
| **判定していないもの** | 美醜の評価、個人の価値、性格や人間性 |

## 10. 改善アドバイス生成

### 10.1 生成ルール

- 判定結果（ランク）と教師データの傾向をもとに、**上位ランクに近づくための具体的な改善ポイント**を提示する
- アドバイスは3〜5項目で構成し、各項目は具体的で実行可能な内容とする

### 10.2 表示方針

- 診断レポートには改善アドバイスを**テキスト形式**で表示する
- ランク以外の数値（類似度の生値など）はユーザーに表示しない（実装時に方針確定）

### 10.3 客観性・透明性

診断レポートには以下を**必ず明示**する:

1. **「本判定は、選別済み画像データとの類似度および傾向分析に基づく客観的結果です。」**
2. **「個人の価値や魅力を断定するものではありません。」**

## 13. AI推論のDocker以外の代替案

仕様書 §16 の提案要求に基づき、AI推論における Docker Compose + GPU 以外の代替方法を整理する。

### 13.1 現行方式: Docker Compose + GPU

**概要**: docker-compose.yml にNVIDIA GPUデバイスを指定し、コンテナ内でAI推論を実行する。

| 項目 | 評価 |
|------|------|
| **メリット** | 環境統一・再現性が高い。開発〜本番まで同一構成。`docker compose up` で即起動 |
| **デメリット** | NVIDIA Container Toolkit のセットアップが必要。ホストにGPUドライバー必須 |
| **推奨度** | ★★★★ |

### 13.2 代替案1: AWS SageMaker Endpoints

**概要**: AWS SageMakerのマネージドエンドポイントとしてモデルをデプロイし、REST APIで推論結果を取得する。

| 項目 | 評価 |
|------|------|
| **メリット** | フルマネージド。オートスケーリング対応。モデルバージョニング管理が容易 |
| **デメリット** | AWSロックイン。本プロジェクトはGCP想定のため整合性に課題。コスト高（常時起動時） |
| **推奨度** | ★★（GCPメインのため非推奨） |

### 13.3 代替案2: GCP Vertex AI

**概要**: GCP Vertex AI の Prediction エンドポイントとしてモデルをデプロイする。

| 項目 | 評価 |
|------|------|
| **メリット** | GCPエコシステムと統合（DB: Cloud SQL, ストレージ: GCS と同一クラウド）。マネージドでスケーラブル |
| **デメリット** | Vertex AI固有のモデル形式への変換が必要。学習コスト。コスト予測が難しい |
| **推奨度** | ★★★（GCPメインなら有力候補） |

### 13.4 代替案3: NVIDIA Triton Inference Server

**概要**: NVIDIA公式の推論サーバー。複数モデルの同時提供、バッチ処理、動的バッチングに対応。

| 項目 | 評価 |
|------|------|
| **メリット** | 高スループット。複数モデル同時管理（RankMeの判定方法切り替えと相性良い）。GPU最適化 |
| **デメリット** | 学習コスト高。セットアップが複雑。小規模では過剰 |
| **推奨度** | ★★（スケール時の移行先候補） |

### 13.5 代替案4: ローカルvenv直接実行（GPU直アクセス）

**概要**: Dockerを使わず、ホストOS上のPython仮想環境（venv）で直接GPU推論を実行する。

| 項目 | 評価 |
|------|------|
| **メリット** | セットアップ最速。GPUへの直アクセスでオーバーヘッド最小。開発初期のプロトタイプに最適 |
| **デメリット** | 環境差異リスク。再現性が低い。本番運用には不向き |
| **推奨度** | ★★★（プロトタイプ段階のみ） |

### 13.6 推奨方針

| フェーズ | 推奨方式 | 理由 |
|---------|---------|------|
| プロトタイプ・開発初期 | ローカルvenv直接実行 | 最速で動作確認。GPUドライバーのみで動作 |
| 開発中期〜デモ | **Docker Compose + GPU**（本命） | 環境統一。チーム開発での再現性確保 |
| 本番スケール時 | **GCP Vertex AI** or Triton | マネージドでスケーラブル。GCPエコシステム統合 |

> **結論**: 開発初期は Docker Compose + GPU を基本とし、スケールが必要になった段階で GCP Vertex AI または NVIDIA Triton Inference Server への移行を検討する。GCPをメインインフラとしているため、長期的には Vertex AI が最も整合性が高い。

## 14. 用語定義

| 用語 | 定義 |
|------|------|
| RankMe | プロの評価基準をAIで再現する**視覚評価プラットフォーム**。顔診断サービスではない |
| ランク | 教師データとの類似度に基づく 1〜10 の段階評価 |
| 教師データ | プロのスカウト実務者によりラベル付けされた、各ランク100枚・合計1,000枚の顔画像 |
| 診断レポート | 現在のランクと改善アドバイスのみを表示する画面・出力 |
| AI推論サービス | ランク判定を行うコンテナ／プロセス。複数実装を設定で切り替え可能 |
| 判定方法（実装） | 共通インターフェースを満たす、モデル・学習方法ごとのランク算出実装。切り替えで差し替え可能 |
| 共通インターフェース | 入力: 顔画像1枚、出力: ランク1〜10。全判定実装がこの契約に従う |
| 外部DB | 診断結果の保存・履歴用。Docker外の**外部インフラ**。**GCP**（Cloud SQL / Firestore 等）を想定 |
| ラベリング手動追加UI | 教師データに画像を登録し、ランク（1〜10）を手動で付与する管理者向けUI。拡張・再ラベリングに使用 |
| ラベリング | 教師データに対してランク（1〜10）を付与する作業。プロのスカウト実務者が統一基準で実施 |
| GCS | Google Cloud Storage。教師データの画像ファイル格納先 |
| Cloud SQL | GCPのマネージドリレーショナルデータベースサービス |
| Firestore | GCPのマネージドドキュメント型データベースサービス |
